Every widget is a white card with the same parts. Learn them once and every widget reads the same way.

Automatic or logged by you?

Automatic widgets read your merged pull requests (GitLab and GitHub), your Jira tickets or your CI builds. You never type into them. They count from 1 January of the current year ("2026 YTD"). If a tool is not connected, connect it under Settings → Integrations.

Logged widgets are filled in by you. Under each one sits a strip of windows, one per week, month or quarter, so you can see which ones you have logged and which you missed.

The cadence strip
It sits under every logged widget once the goal is ready to track. The header reads "This cycle" and counts only the windows that were due so far, for example "7 of 9 months logged". Long cycles, such as a year of weeks, show as a compact grid of small squares instead of labelled cells.

Using it
Click a past or current square to log that window. The panel says "Logging …" and has "Nothing to report" (settles a quiet window so it stops counting as missed; click "Reopen" to undo) and "Close". In the app the current window has a dashed outline, the only dashed line in the app.
Before this tracker
Windows before the tracker was created (or before your hire date) are never counted as missed. They are hidden behind "Backfill earlier … (N)" if you want to fill them in anyway.

Tiers (grade levels)
Goals with a ladder are graded on four levels. The colour is the same everywhere in the app: peach is "Not achieved", mint is "Achieved", sky is "Over achieved", lilac is "Role model".
Per-window grading
When a goal has levels for each window, the open window shows "This window's tier" with "Grade window" or "Re-grade window". If the goal has no per-window levels, a grey chip says "Same ladder as the whole goal — add per-window levels under Edit levels". When a manager owns the levels, it adds "(manager-governed)".

The share of your PRs this year that pass a checklist you wrote (for example "has tests", "describes the why"). Each PR gets "Pass" (mint) or "Fail" (peach).

What it measures
Whatever the plan asks for, one form per window. Each window of a plan can have its own name ("Week 3 — Prompt patterns"), due date, prompt and fields. The top label shows the cadence, or "one-time".
Data comes from
Mostly you. Some fields fill themselves from your repositories (lilac "Auto" badge). Closing a period's GitHub issue can also log that period for you (it then shows a "From GitHub" badge).
Cadence
The plan's own: weekly, monthly, quarterly and so on. A window can contain a second cadence (for example a quarter with its own weeks). Plans for people leads can have a second "Management plan" section, with a list of the lead's reports.
States

Plan length
The plan's start and end come from the document. If it has no stated length, the cycle falls back to the calendar year. Check this with "Edit plan" under "More".

The eight field types
  • yes / no: a tick box. The answer reads "Yes" or "Not yet".
  • count: − and + buttons, with an optional unit and target.
  • 1–5: a five-step rating.
  • number: a measured value, with an optional unit and target.
  • note: short free text.
  • date: a date picker.
  • choice: one option from a fixed list.
  • link: a URL. The link is the evidence, so there is no separate proof box.
Answer and proof
Every field except a link has two halves: "Answer" (your claim) and "Proof" (a note, link or measured value that backs it up). Proof is only asked for (lemon "Add proof") once you have answered and the field is not optional. Otherwise the button is a quiet "Add a note".
Grading
The AI grader reads both halves. A claim with no proof is weaker evidence.

What they are
Fields inside a composed tracker that read their answer from GitHub or GitLab, so you never type them. They carry a lilac "Auto · github" or "Auto · gitlab" badge, and the second half is called "Source" instead of "Proof".
The seven checks
  • "File exists in repo": shows "Present" or "Missing".
  • "File last updated": the date of the newest commit to a file.
  • "Matching pull requests": how many of your PRs this year match a search.
  • "Labelled pull requests": how many of your merged PRs this year carry a label.
  • "Open pull requests": how many are open right now in a repository.
  • "Issue closed": "Closed" or "Open" for a GitHub issue (GitHub only).
  • "Issue task list": how much of a GitHub issue's task list is ticked, as a percentage (GitHub only).
States
"Not connected — link the provider in Settings" when the tool isn't connected, or "Couldn't read this yet", each with "Retry". "Check on GitHub" / "Check on GitLab" opens the same search on the provider.
Safety
The AI can only pick from these seven checks. It never writes its own web address.

GitHub, read back about once an hour with your own token. Click the refresh icon to re-read it now.
States
Sky "Open on GitHub" (with ticked tasks if the issue has a task list). Mint "Closed on GitHub": closing an issue as completed logs that period as done. "Closed · not planned" does not log anything. Peach "Publish failed" or "Issue not found" offer "Republish" or "Unlink". Lemon "Reconnect GitHub" means the GitHub connection needs renewing.
